# Технічне завдання
## Розробка високопродуктивного CUDA-коду для прямого N-body моделювання гравітаційних систем методом Ерміта 4-го порядку з адаптивним часовим кроком

**Версія:** 1.0  
**Мова програмування:** C++ / CUDA C++  
**Обчислювальна платформа:** NVIDIA GPU (одна або декілька відеокарт)  
**Основний метод інтегрування:** 4th-order Hermite integrator  
**Тип адаптації:** індивідуальні адаптивні часові кроки (individual/block time steps)

---

# 1. Мета та призначення програми

Розробити високопродуктивний програмний комплекс для прямого чисельного моделювання еволюції гравітаційних N-body систем із використанням обчислювальних можливостей GPU та технології CUDA.

Основним чисельним методом має бути інтегратор Ерміта четвертого порядку (4th-order Hermite scheme) з адаптивним вибором часових кроків для кожної частинки.

Програма повинна забезпечувати моделювання систем, що складаються з:

- одного масивного центрального тіла;
- від \(128\,000\) до \(1\,024\,000\) (128k–1024k) частинок меншої маси;
- довільного просторового розподілу частинок;
- довільного розподілу мас частинок;
- систем, у яких сумарна маса частинок може бути порівнянною з масою центрального тіла або навіть наближатися до неї.

Важливою особливістю задачі є те, що центральне тіло не можна апріорі вважати нерухомим. Якщо сумарна маса частинок порівнянна з його масою, необхідно враховувати рух центрального тіла під дією гравітаційного поля всієї системи.

Основні вимоги до програмного комплексу:

1. Висока продуктивність обчислень на GPU.
2. Масштабування на декілька GPU.
3. Четвертий порядок точності інтегрування.
4. Індивідуальні адаптивні часові кроки.
5. Контроль точності на основі збереження повної механічної енергії.
6. Можливість моделювання тривалої динамічної еволюції системи.
7. Відтворюваність результатів та можливість перевірки чисельної точності.

**Основна вимога до точності:**

Відносна зміна повної механічної енергії системи протягом одного характерного середнього орбітального періоду повинна становити не більше

\[
\boxed{
\frac{|\Delta E|}{|E_0|}\leq 10^{-8}.
}
\]

Це значення слід розглядати як основний критерій приймання чисельного інтегратора, а не як гарантовану властивість методу Ерміта незалежно від параметрів моделювання.

# 2. Фізична модель

## 2.1. Рівняння руху

Для системи з \(N\) гравітаційно взаємодіючих тіл необхідно розв'язувати рівняння:

\[
\frac{d\mathbf r_i}{dt}=\mathbf v_i,
\]

\[
\frac{d\mathbf v_i}{dt}=\mathbf a_i,
\]

де прискорення кожної частинки визначається гравітаційною взаємодією з усіма іншими частинками:

\[
\mathbf a_i =
G\sum_{\substack{j=0\\j\neq i}}^{N}
m_j
\frac{\mathbf r_j-\mathbf r_i}
{|\mathbf r_j-\mathbf r_i|^3}.
\]

За необхідності передбачити можливість використання Plummer softening:

\[
\mathbf a_i =
G\sum_{\substack{j=0\\j\neq i}}^{N}
m_j
\frac{\mathbf r_j-\mathbf r_i}
{\left(|\mathbf r_j-\mathbf r_i|^2+\epsilon^2\right)^{3/2}},
\]

де \(\epsilon\) — параметр згладжування потенціалу.

За замовчуванням основний режим моделювання повинен відповідати незгладженій ньютонівській гравітації:

\[
\epsilon=0.
\]

Softening має бути опціональним параметром.

**Важливо:** softening не повинен використовуватися як спосіб штучного забезпечення енергетичної точності. Він змінює фізичну модель системи.

## 2.2. Центральне тіло

Центральне тіло повинно бути повноцінним учасником N-body системи.

Для нього необхідно розраховувати:

- координати;
- швидкість;
- прискорення;
- похідну прискорення (jerk);
- адаптивний часовий крок.

Його рух визначається гравітаційним впливом усіх інших частинок.

Забороняється реалізовувати центральне тіло як нерухомий зовнішній потенціал у стандартному режимі моделювання.

Програма повинна підтримувати два режими:

1. **Self-consistent N-body:** центральне тіло та всі частинки інтегруються динамічно.
2. **Fixed-center approximation:** центральне тіло нерухоме, а частинки рухаються в його потенціалі. Використовується виключно для тестів та порівнянь.

# 3. Чисельний метод: інтегратор Ерміта четвертого порядку

## 3.1. Загальна схема

Необхідно реалізувати класичну схему 4th-order Hermite integrator.

Для кожної частинки на поточному часовому кроці відомі:

\[
\mathbf r_i,\quad
\mathbf v_i,\quad
\mathbf a_i,\quad
\mathbf j_i,
\]

де:

\[
\mathbf j_i=\frac{d\mathbf a_i}{dt}
\]

— похідна прискорення за часом.

Метод використовує прогнозування (predictor) та корекцію (corrector).

## 3.2. Predictor

Для прогнозування координат та швидкостей на момент \(t+\Delta t\) використовуються:

\[
\mathbf r_{i,p} =
\mathbf r_i+
\mathbf v_i\Delta t+
\frac{1}{2}\mathbf a_i\Delta t^2+
\frac{1}{6}\mathbf j_i\Delta t^3,
\]

\[
\mathbf v_{i,p} =
\mathbf v_i+
\mathbf a_i\Delta t+
\frac{1}{2}\mathbf j_i\Delta t^2.
\]

Ці операції повинні виконуватися паралельно на GPU.

## 3.3. Обчислення прискорення та jerk

На прогнозованих координатах необхідно обчислити нові значення:

\[
\mathbf a_{i,1},\quad \mathbf j_{i,1}.
\]

Для незгладженої гравітації:

\[
\mathbf r_{ij}=\mathbf r_j-\mathbf r_i,
\]

\[
\mathbf v_{ij}=\mathbf v_j-\mathbf v_i,
\]

\[
r_{ij}^2=\mathbf r_{ij}\cdot\mathbf r_{ij}.
\]

Прискорення:

\[
\mathbf a_i =
G\sum_{j\neq i}
m_j\frac{\mathbf r_{ij}}{r_{ij}^3}.
\]

Jerk:

\[
\mathbf j_i =
G\sum_{j\neq i}
m_j
\left[
\frac{\mathbf v_{ij}}{r_{ij}^3}
-
3\frac{
(\mathbf r_{ij}\cdot\mathbf v_{ij})\mathbf r_{ij}
}{r_{ij}^5}
\right].
\]

Для підвищення продуктивності потрібно спільно обчислювати прискорення та jerk в одному CUDA kernel.

Бажано використовувати попередньо розраховані величини:

\[
u=\frac{1}{r^2},\qquad
u_3=u\sqrt{u},\qquad
u_5=u_3u.
\]

Це дозволить уникнути повторних обчислень.

## 3.4. Corrector

Після отримання нового прискорення та jerk необхідно скоригувати координати та швидкості:

\[
\mathbf v_{i,new} =
\mathbf v_i+
\frac{1}{2}
(\mathbf a_i+\mathbf a_{i,1})\Delta t
+
\frac{1}{12}
(\mathbf j_i-\mathbf j_{i,1})\Delta t^2,
\]

\[
\mathbf r_{i,new} =
\mathbf r_i+
\frac{1}{2}
(\mathbf v_i+\mathbf v_{i,new})\Delta t
+
\frac{1}{12}
(\mathbf a_i-\mathbf a_{i,1})\Delta t^2.
\]

Корекція повинна виконуватися для активних частинок на поточному часовому кроці.

Після корекції зберігаються оновлені значення:

\[
\mathbf r_i,\quad
\mathbf v_i,\quad
\mathbf a_i,\quad
\mathbf j_i.
\]

---

## 3.5. Оцінка похідних прискорення: snap та crackle

Для адаптивного вибору часового кроку необхідно оцінювати наступні похідні прискорення:

\[
\mathbf s_i=\frac{d^2\mathbf a_i}{dt^2},
\qquad
\mathbf c_i=\frac{d^3\mathbf a_i}{dt^3}.
\]

Вони можуть бути отримані з попередніх і нових значень прискорення та jerk:

\[
\mathbf s_i =
\frac{
-6(\mathbf a_i-\mathbf a_{i,1})
-\Delta t(4\mathbf j_i+2\mathbf j_{i,1})
}{\Delta t^2},
\]

\[
\mathbf c_i =
\frac{
12(\mathbf a_i-\mathbf a_{i,1})
+6\Delta t(\mathbf j_i+\mathbf j_{i,1})
}{\Delta t^3}.
\]

Ці величини необхідні для визначення оптимального індивідуального часового кроку.

## 3.6. Адаптивний часовий крок

Реалізувати критерій Aarseth для 4-го порядку методу Ерміта:

\[
\boxed{
\Delta t_i =
\sqrt{
\eta
\frac{
|\mathbf a_i||\mathbf s_i|+|\mathbf j_i|^2
}{
|\mathbf j_i||\mathbf c_i|+|\mathbf s_i|^2
}
}.
}
\]

Тут:

- \(\eta\) — параметр точності інтегрування;
- \(\mathbf a_i\) — прискорення;
- \(\mathbf j_i\) — jerk;
- \(\mathbf s_i\) — snap;
- \(\mathbf c_i\) — crackle.

Параметр \(\eta\) повинен задаватися користувачем.

Передбачити початковий рекомендований діапазон:

\[
0.001\leq\eta\leq0.02.
\]

Остаточне значення \(\eta\) необхідно визначати експериментально за результатами тестів збереження енергії.

**Важливо:** не можна вважати, що конкретне значення \(\eta\) автоматично гарантує точність \(10^{-8}\). Потрібно забезпечити можливість автоматичного підбору цього параметра за результатами контрольних інтегрувань.

## 3.7. Individual block time steps

Для систем із кількістю частинок до мільйона необхідно реалізувати індивідуальні часові кроки з використанням block time-step scheme.

Ідея полягає в тому, що кожна частинка має власний часовий крок, але всі часові кроки повинні бути кратними степеням двійки відносно базового кроку:

\[
\Delta t_i = \frac{\Delta t_{\max}}{2^{k_i}},
\]

де \(k_i\) — ціле невід'ємне число.

Такий підхід дозволяє:

- зменшити кількість непотрібних обчислень;
- ефективніше обробляти частинки з різними орбітальними періодами;
- синхронізувати обчислення на GPU;
- уникати повного перерахунку всіх частинок на кожному часовому кроці.

Необхідно реалізувати:

1. Визначення індивідуального оптимального кроку.
2. Округлення кроку до найближчого допустимого значення за схемою block time steps.
3. Визначення списку активних частинок.
4. Прогнозування координат і швидкостей усіх частинок на поточний момент часу.
5. Обчислення прискорення та jerk для активних частинок.
6. Корекцію стану активних частинок.
7. Оновлення їхніх індивідуальних часових кроків.

Для кожної частинки необхідно зберігати:

```cpp
struct Particle {
    double mass;

    double3 pos;
    double3 vel;

    double3 acc;
    double3 jerk;

    double3 snap;
    double3 crackle;

    double time;
    double dt;

    int64_t next_time;
    int level;
};
```

Це логічна структура даних. Для GPU бажано використовувати SoA (Structure of Arrays), щоб забезпечити ефективний доступ до пам'яті.

Наприклад:

```cpp
double *mass;
double3 *pos;
double3 *vel;
double3 *acc;
double3 *jerk;
double *dt;
int64_t *next_time;
```

Для зменшення витрат пам'яті та покращення пропускної здатності необхідно уникати зберігання даних, які можна швидко відновити.

# 4. Архітектура CUDA-обчислень

## 4.1. Загальні вимоги

Основні обчислення повинні виконуватися на GPU.

CPU використовується для:

- ініціалізації системи;
- керування інтегруванням;
- формування списків активних частинок;
- контролю часових кроків;
- збереження результатів;
- розрахунку та контролю глобальних фізичних величин;
- обробки конфігураційних параметрів.

GPU використовується для:

- прогнозування координат та швидкостей;
- розрахунку гравітаційних прискорень;
- розрахунку jerk;
- корекції координат і швидкостей;
- оцінювання похідних прискорення;
- визначення адаптивних часових кроків;
- обчислення діагностичних фізичних величин.

Необхідно мінімізувати передачу даних між CPU та GPU.

## 4.2. Прямий метод N-body

Для початкової версії необхідно реалізувати прямий алгоритм обчислення гравітаційних взаємодій.

Обчислювальна складність:

\[
O(N^2).
\]

Для \(N=10^6\) кількість парних взаємодій становить приблизно:

\[
N(N-1)\approx10^{12}.
\]

При цьому кожна взаємодія потребує розрахунку внесків у прискорення та jerk.

Незважаючи на значну обчислювальну складність, прямий метод є бажаним для цієї задачі, оскільки:

- не вносить просторових апроксимацій;
- дозволяє точно контролювати гравітаційні взаємодії;
- добре підходить для GPU;
- забезпечує контрольовану чисельну похибку;
- дозволяє коректно досліджувати близькі гравітаційні взаємодії.

## 4.3. CUDA kernel для розрахунку прискорення та jerk

Основним обчислювальним ядром має бути:

```cpp
__global__
void calculate_acc_jerk(
    int N,
    const double3 *pos,
    const double3 *vel,
    const double *mass,
    const int *active,
    int N_active,
    double3 *acc,
    double3 *jerk
);
```

Призначення:

Для кожної активної частинки обчислити сумарне прискорення та jerk від усіх інших частинок.

Рекомендована схема:

- один CUDA thread відповідає за одну цільову частинку;
- потоки організовуються в CUDA blocks;
- координати та швидкості частинок-джерел завантажуються в shared memory;
- кожен блок обробляє групу частинок-джерел;
- накопичення прискорення та jerk виконується в регістрах;
- результат записується в глобальну пам'ять після завершення обробки всіх джерел.

Для зменшення кількості звернень до глобальної пам'яті необхідно застосовувати tiled N-body алгоритм.

Схематично:

```cpp
for (int tile = 0; tile < N; tile += BLOCK_SIZE)
{
    load_sources_to_shared_memory();

    __syncthreads();

    calculate_pairwise_interactions();

    __syncthreads();
}

store_acc_jerk();
```

Потрібно окремо оптимізувати:

- розмір CUDA block;
- кількість потоків на одну цільову частинку;
- розмір tile;
- використання регістрів;
- пропускну здатність пам'яті;
- occupancy GPU.

Необхідно уникати атомарних операцій при накопиченні прискорення та jerk, якщо їх можна замінити локальним накопиченням у регістрах.

## 4.4. Числова точність

Для забезпечення заданої точності необхідно використовувати:

\[
\texttt{double}
\]

для всіх основних фізичних величин.

Вимоги:

- координати — double;
- швидкості — double;
- маси — double;
- прискорення — double;
- jerk — double;
- часові кроки — double;
- енергія — double.

Забороняється використовувати float для основних обчислень гравітаційних взаємодій у базовій реалізації.

Додатково необхідно передбачити:

1. Контроль переповнення та некоректних значень.
2. Контроль \(r_{ij}^2\) перед обчисленням обернених степенів.
3. Захист від NaN та Inf.
4. Використання стабільного алгоритму підсумовування для діагностичних сум.
5. Можливість відключення fast-math оптимізацій.

Особливу увагу потрібно приділити точності обчислення повної енергії. Для цього бажано використовувати попарне або компенсоване підсумовування.

# 5. Підтримка декількох GPU

## 5.1. Загальна архітектура

Програма повинна підтримувати запуск на одній або декількох NVIDIA GPU.

Для багатокарткової конфігурації передбачити використання CUDA streams, CUDA events та, за можливості, CUDA-aware MPI або NCCL.

Рекомендована початкова архітектура — replicated source data + distributed target particles.

Принцип роботи:

1. Усі GPU містять повний набір частинок-джерел.
2. Цільові частинки розподіляються між GPU.
3. Кожна GPU обчислює прискорення та jerk для власної групи цільових частинок.
4. Після корекції активних частинок оновлені дані синхронізуються між GPU.
5. Наступний часовий крок починається після завершення необхідної синхронізації.

Для \(N_{\rm GPU}\) карток:

\[
N_{\rm target}^{(k)}
\approx
\frac{N_{\rm active}}{N_{\rm GPU}}.
\]

Це дозволяє масштабувати обчислення без необхідності виконувати міжкарткові редукції прискорень.

## 5.2. Синхронізація

Необхідно забезпечити:

- синхронізацію координат і швидкостей;
- синхронізацію активних частинок;
- узгодження глобального часу;
- коректне оновлення центрального тіла;
- контроль завершення всіх GPU kernel;
- відсутність використання застарілих даних.

Для невеликої кількості GPU допустиме дублювання повного масиву джерел у пам'яті кожної карти.

Для великих конфігурацій необхідно передбачити можливість використання peer-to-peer передачі даних.

## 5.3. Балансування навантаження

Оскільки кількість активних частинок змінюється з часом, статичний розподіл може призводити до нерівномірного завантаження GPU.

Потрібно реалізувати динамічний розподіл активних частинок між GPU.

Критеріями оцінювання повинні бути:

- кількість активних частинок;
- час виконання попереднього кроку;
- обсяг переданих даних;
- завантаження GPU.

# 6. Обчислення та контроль енергії

Цей розділ є одним із найважливіших у всьому проєкті.

## 6.1. Повна механічна енергія

Для системи з \(N\) частинок повна енергія:

\[
E=K+U,
\]

де кінетична енергія:

\[
K=\frac12\sum_{i=0}^{N-1}m_i v_i^2,
\]

а потенціальна енергія:

\[
U=-G\sum_{i=0}^{N-1}
\sum_{j=i+1}^{N-1}
\frac{m_i m_j}{r_{ij}}.
\]

Для моделі з Plummer softening:

\[
U=-G\sum_{i=0}^{N-1}
\sum_{j=i+1}^{N-1}
\frac{m_i m_j}
{\sqrt{r_{ij}^2+\epsilon^2}}.
\]

Енергія повинна включати всі тіла системи, зокрема центральне тіло.

Забороняється розраховувати енергію лише для частинок, ігноруючи кінетичну енергію центрального тіла.

## 6.2. Критерій збереження енергії

Основний критерій:

\[
\delta_E(t)=
\frac{|E(t)-E(0)|}{|E(0)|}.
\]

Вимога:

\[
\boxed{
\delta_E(T_{\rm mean})\leq10^{-8}.
}
\]

Для контролю тривалої еволюції необхідно також розраховувати:

\[
\delta_{E,\max}(T)=
\max_{0\leq t\leq T}
\frac{|E(t)-E(0)|}{|E(0)|}.
\]

Вихідні результати повинні містити:

- початкову енергію;
- поточну енергію;
- абсолютну зміну енергії;
- відносну зміну енергії;
- максимальне відхилення;
- середнє відхилення за період;
- час інтегрування.

Важливо розрізняти два показники:

1. Відхилення енергії між початком та кінцем одного періоду.
2. Максимальне відхилення енергії в будь-який момент цього періоду.

Для приймання програми рекомендовано вимагати виконання критерію \(10^{-8}\) саме для максимального відхилення, а не лише для різниці між початковим і кінцевим значеннями.

## 6.3. Визначення характерного орбітального періоду

Для системи з широким розподілом орбітальних періодів необхідно передбачити визначення характерного середнього періоду.

Рекомендовано використовувати кілька діагностичних величин:

- середній орбітальний період;
- медіанний орбітальний період;
- масозважений середній орбітальний період.

Для частинки, що рухається навколо центрального тіла, початкову оцінку можна отримати з:

\[
P_i=2\pi
\sqrt{\frac{a_i^3}{G(M_c+m_i)}},
\]

де \(a_i\) — велика піввісь її орбіти відносно центрального тіла.

Однак, коли сумарна маса частинок порівнянна з масою центрального тіла, ця формула є лише наближенням. Для таких систем потрібно додатково враховувати колективний потенціал.

У конфігураційному файлі користувач повинен мати можливість задати характерний період вручну.

# 7. Особливі фізичні та чисельні випадки

## 7.1. Близькі гравітаційні зближення

Програма повинна коректно обробляти ситуації, коли відстань між двома частинками стає дуже малою.

Необхідно передбачити:

- автоматичне зменшення локального часового кроку;
- контроль мінімальної відстані;
- виявлення надто малих часових кроків;
- контроль чисельної нестабільності;
- повідомлення про потенційне зіткнення.

## 7.2. Зіткнення частинок

Необхідно передбачити опціональний модуль обробки фізичних зіткнень.

Можливі режими:

1. Відсутність фізичних зіткнень (point masses).
2. Виявлення зіткнень за заданими радіусами.
3. Ідеально непружне злиття частинок із збереженням маси та імпульсу.

Для першої версії достатньо реалізувати режим point masses і детектор близьких зближень.

Злиття частинок має бути окремим модулем, оскільки воно змінює структуру системи та потребує спеціального контролю енергії.

## 7.3. Збереження імпульсу та моменту імпульсу

Крім енергії необхідно контролювати:

Повний імпульс:

\[
\mathbf P=\sum_i m_i\mathbf v_i.
\]

Повний момент імпульсу:

\[
\mathbf L=\sum_i m_i(\mathbf r_i\times\mathbf v_i).
\]

Відносні зміни:

\[
\delta_P=
\frac{|\mathbf P(t)-\mathbf P(0)|}
{P_{\rm scale}},
\]

\[
\delta_L=
\frac{|\mathbf L(t)-\mathbf L(0)|}
{L_{\rm scale}}.
\]

Масштаби нормування необхідно визначити з початкових характеристик системи, щоб уникнути ділення на нуль при малих або нульових початкових значеннях.

Ці діагностичні параметри дозволять виявляти помилки синхронізації між GPU та чисельні похибки.

# 8. Оптимізація продуктивності

## 8.1. Основні напрямки оптимізації

Пріоритетними напрямками оптимізації CUDA-коду повинні бути:

1. Мінімізація кількості операцій із глобальною пам'яттю.
2. Максимальне використання shared memory.
3. Зменшення кількості операцій ділення та обчислення квадратного кореня.
4. Векторизація обчислень.
5. Мінімізація синхронізацій між CUDA blocks.
6. Ефективне формування списків активних частинок.
7. Використання асинхронних передач даних між GPU.
8. Мінімізація передач даних між CPU та GPU.

Особливу увагу приділити реалізації ядра обчислення прискорення та jerk, оскільки воно визначатиме основну частину обчислювальних витрат.

## 8.2. Можливість використання Tensor Cores

У базовій реалізації не використовувати Tensor Cores для основних обчислень.

Можливість застосування змішаних форматів точності може розглядатися лише в майбутньому після підтвердження, що вони не погіршують енергетичну точність.

## 8.3. Використання GPU для діагностики

Обчислення повної енергії, імпульсу та моменту імпульсу бажано виконувати безпосередньо на GPU.

Для потенціальної енергії потрібно реалізувати окремий CUDA kernel із використанням унікальних пар частинок:

\[
U=-G\sum_{i<j}\frac{m_im_j}{r_{ij}}.
\]

Необхідно уникати подвійного підрахунку взаємодій.

Для підсумовування використовувати ієрархічну редукцію з подальшим компенсованим підсумовуванням результатів на CPU або GPU.

Діагностику енергії не потрібно виконувати після кожного інтеграційного кроку. Частоту діагностики задавати параметром конфігурації.

# 9. Структура програмного комплексу

Рекомендовано розділити програму на незалежні модулі.

| Модуль | Призначення |
|---|---|
| `NBodySystem` | Зберігання параметрів системи |
| `ParticleData` | Масиви параметрів частинок |
| `HermiteIntegrator` | Реалізація методу Ерміта |
| `Predictor` | Прогнозування координат та швидкостей |
| `Corrector` | Корекція координат та швидкостей |
| `GravityKernel` | Розрахунок прискорення та jerk |
| `TimeStepController` | Визначення адаптивних часових кроків |
| `BlockStepScheduler` | Керування активними частинками |
| `GPUManager` | Керування однією або декількома GPU |
| `EnergyCalculator` | Розрахунок кінетичної та потенціальної енергії |
| `Diagnostics` | Контроль енергії, імпульсу та моменту імпульсу |
| `SnapshotWriter` | Запис результатів моделювання |
| `SimulationConfig` | Завантаження параметрів моделювання |

Бажано, щоб усі модулі мали незалежні інтерфейси. Це дозволить у майбутньому замінити інтегратор або додати нові фізичні моделі без переписування GPU-обчислень.

## 9.1. Основний цикл програми

Загальна логіка:

```cpp
initialize_system();
initialize_gpu();

calculate_initial_acceleration();
calculate_initial_jerk();

initialize_time_steps();

while (simulation_time < end_time)
{
    determine_next_global_time();

    predict_all_particles();

    select_active_particles();

    calculate_acceleration_and_jerk();

    correct_active_particles();

    estimate_snap_crackle();

    update_individual_time_steps();

    synchronize_gpus_if_required();

    if (diagnostics_required)
    {
        calculate_energy();
        calculate_momentum();
        calculate_angular_momentum();

        write_diagnostics();
    }

    if (snapshot_required)
    {
        write_snapshot();
    }
}

finalize_simulation();
```

Це логічна схема. Реалізація повинна враховувати асинхронне виконання CUDA kernel та можливість перекриття обчислень із передачею даних.

**Важлива технічна деталь:** для individual block time steps прогнозування повинно забезпечувати координати та швидкості всіх частинок саме на поточний глобальний момент часу. Не можна використовувати застарілі координати неактивних частинок при обчисленні прискорення активних частинок.

# 11. Тестування та перевірка точності

Програмний комплекс повинен пройти декілька етапів тестування.

## 11.1. Тест 1. Задача двох тіл

Використати центральне тіло та одну частинку.

Перевірити:

- правильність кеплерівської орбіти;
- збереження енергії;
- збереження моменту імпульсу;
- правильність адаптивного часового кроку;
- четвертий порядок збіжності інтегратора.

Порівняти чисельні координати з аналітичним розв'язком задачі двох тіл.

## 11.2. Тест 2. Задача трьох тіл

Перевірити:

- правильність взаємного гравітаційного впливу;
- рух центрального тіла;
- збереження повного імпульсу;
- збереження повного моменту імпульсу;
- точність інтегрування при різних масах тіл.

## 11.3. Тест 3. Система з 128k частинок

Створити систему:

- одне масивне центральне тіло;
- 128 000 частинок;
- приблизно кеплерівський розподіл орбіт;
- сумарна маса частинок становить 10–100% маси центрального тіла.

Виконати інтегрування протягом декількох характерних орбітальних періодів.

Перевірити енергетичну точність.

## 11.4. Тест 4. Система з 1M частинок

Повторити тест для:

\[
N=1\,024\,000.
\]

Оцінити:

- продуктивність;
- завантаження GPU;
- використання відеопам'яті;
- масштабування на декілька GPU;
- стабільність адаптивного інтегрування.

## 11.5. Тест 5. Порівняння CPU та GPU

Для систем із невеликою кількістю частинок виконати однакове інтегрування:

1. На CPU.
2. На одній GPU.
3. На двох GPU.
4. На доступній багатокартковій конфігурації.

Порівняти результати:

- координати;
- швидкості;
- повну енергію;
- повний імпульс;
- момент імпульсу.

Розбіжності між реалізаціями повинні відповідати очікуваним похибкам чисельного інтегрування та арифметики.

## 11.6. Тест 6. Перевірка порядку збіжності

Необхідно перевірити, чи реалізація дійсно має четвертий порядок точності.

Для цього виконати інтегрування однієї системи з послідовним зменшенням максимального часового кроку:

\[
h,\quad h/2,\quad h/4,\quad h/8.
\]

Для фіксованого інтервалу часу порівняти похибку з високоточною контрольною траєкторією.

Для методу четвертого порядку очікується:

\[
\frac{e(h)}{e(h/2)}\approx16
\]

у режимі асимптотичної збіжності.

# 15. Важливі зауваження щодо чисельної реалізації

Є декілька моментів, які я рекомендую врахувати ще на етапі проєктування.

### 15.1. Метод Ерміта не є симплектичним

Класичний Hermite 4th-order integrator має четвертий порядок точності, але не є симплектичним інтегратором.

Тому навіть за малого часового кроку можливий систематичний дрейф енергії при тривалому інтегруванні.

Для поставленої задачі це не є причиною відмовлятися від методу Ерміта, але необхідно контролювати не тільки максимальну зміну енергії за один період, а й довготривалий дрейф.

### 15.2. Індивідуальні часові кроки та енергетична точність

Використання індивідуальних часових кроків значно підвищує продуктивність, проте може ускладнювати забезпечення точного збереження енергії.

Особливо це важливо для систем, у яких:

- частинки мають широкий діапазон орбітальних періодів;
- відбуваються близькі зближення;
- центральне тіло рухається;
- сумарна маса частинок порівнянна з масою центрального тіла.

Тому рекомендую передбачити два режими:

**Режим A — Global time step**

Усі частинки інтегруються з однаковим часовим кроком.

Використовується для перевірки точності та порівняння з еталонними розрахунками.

**Режим B — Individual block time steps**

Кожна частинка має власний адаптивний часовий крок.

Використовується для основних високопродуктивних розрахунків.

### 15.3. Обробка близьких зближень

Для незгладженого гравітаційного потенціалу близькі зближення можуть вимагати дуже малих часових кроків.

У таких випадках стандартний Hermite 4 може бути недостатньо ефективним.

У перспективі варто розглянути:

- Hermite 4 з регуляризацією близьких пар;
- алгоритм KS regularization;
- алгоритми chain regularization.

Для першої версії достатньо реалізувати контроль близьких зближень і адаптивне зменшення кроку.

### 15.4. Визначення критерію енергетичної точності

Я рекомендую використовувати саме:

\[
\boxed{
\max_{t\in[0,T_{\rm mean}]}
\left|
\frac{E(t)-E(0)}{E(0)}
\right|
\leq10^{-8}.
}
\]

Це суворіша вимога, ніж просте порівняння енергії на початку та наприкінці орбітального періоду.

Водночас необхідно враховувати, що вимірювання енергії для системи з мільйоном частинок саме по собі потребує значних обчислювальних ресурсів.

# 16. Моя рекомендація щодо архітектури першої версії

Я б рекомендував реалізувати програму в такій послідовності:

**1. CPU reference implementation**

Повноцінна реалізація Hermite 4 з адаптивними індивідуальними часовими кроками. Вона буде використовуватися для перевірки правильності GPU-версії.

**2. CUDA direct N-body kernel**

Основне ядро обчислення прискорення та jerk з використанням double precision і shared memory.

**3. GPU-based block time-step scheduler**

Формування списку активних частинок та керування адаптивними часовими кроками.

**4. Multi-GPU implementation**

Розподіл цільових частинок між GPU з реплікацією масивів джерел.

**5. Energy monitoring**

Повний контроль енергії, імпульсу та моменту імпульсу.

**6. Performance optimization**

Оптимізація швидкодії після підтвердження чисельної точності.

## 17. Додаткове технічне рішення, яке варто розглянути

Є один важливий аспект, який може суттєво вплинути на продуктивність.

Для системи з \(10^6\) частинок пряме обчислення всіх парних взаємодій потребує приблизно \(10^{12}\) взаємодій за один повний перерахунок прискорень.

Але при використанні individual block time steps не всі частинки потребують корекції на кожному кроці.

Тому я рекомендую передбачити два незалежні рівні оптимізації:

- **Level 1:** обчислення прискорення та jerk тільки для активних частинок.
- **Level 2:** ефективне прогнозування координат і швидкостей усіх частинок на поточний момент часу.

Це дозволить істотно скоротити обчислювальні витрати, особливо коли система містить частинки з різними орбітальними періодами.

При цьому не потрібно переходити до Barnes–Hut або TreePM на першому етапі: прямий метод дозволить отримати контрольовану точність та надійну базову реалізацію.

---

**Підсумкова рекомендація:** для цієї задачі я вважаю оптимальною початковою архітектурою CUDA Direct N-body + Hermite 4 + Aarseth individual block time steps + double precision + multi-GPU replication.

Це дасть змогу побудувати точний і масштабований інтегратор, який можна буде використовувати для довготривалого моделювання систем із мільйоном частинок, включно з випадками, коли маса диска або ансамблю частинок порівнянна з масою центрального об'єкта.

Особливо важливо: **вимогу \(10^{-8}\) потрібно підтвердити чисельними тестами, а не просто задати як параметр програми.** Для цього необхідно передбачити автоматичне тестування збіжності за параметром \(\eta\), максимальним часовим кроком та тривалістю інтегрування.
